# 既存の部屋予約を照合する

古い予約の作成日だけを根拠に一括削除しません。D1予約とDO snapshot、接続、未保存釣果、アラームを照合して扱います。

管理経路はMIGRATION_ADMIN_TOKENが未設定・不正・期限切れの場合404を返します。値は「Unix millisecondsの絶対期限 + ピリオド + 32byteの乱数をbase64url化した43文字」です。ブラウザーへ配信せず、作業用プロセスとWorker secretだけで保持します。短い期限を付け、作業後はsecretも削除します。

## 手順

1. 本番変更前のD1バックアップと復旧地点を記録します。バックアップの機微情報をGit、PR、共有ログへ含めません。
2. 承認された作業枠で専用secretを設定し、同じ値を実行プロセスのMIGRATION_ADMIN_TOKENへ渡します。Worker secretの設定・削除は本番操作です。
3. まず npm run rooms:inspect を実行します。既定はapply=falseであり、期限も予約も変更しません。
4. 結果と承認範囲を確認した後、npm run rooms:reconcile を実行します。集計結果はroom IDやsecretを出力しません。
5. 30分の猶予後に再度inspectし、予約の回収と未保存釣果の保存を確認します。
6. 専用secretを削除します。削除し忘れても絶対期限を過ぎれば管理経路は閉じます。

接続中の表示端末がある部屋は保持します。表示端末がなくアラームもない既存snapshotには、新しい30分の猶予を設定します。未保存釣果の保存と削除は通常のalarm処理に任せます。snapshotが存在しない予約は、作成後30分以上経過し、同一の作成日時を持つ行だけを削除します。直近の作成処理と競合する予約は保持します。

HTTP境界は最大20件ずつ、同時DO要求4件までです。管理用DOパスはWorkerが内部stubへ送る専用経路であり、公開WebSocket URLからパスを書き換える仕組みはありません。

ROOM_ADMIN_ORIGINで分離環境を指定できます。CLIはこのプロジェクトのworkers.devホストとloopbackだけを受け付け、誤った外部ホストへsecretを転送しません。

今回の変更で旧Cloud Runの設定やデータを変更する処理は追加しません。
