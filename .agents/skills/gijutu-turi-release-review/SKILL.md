# 技術釣りの差分整理・PR・リリース

## 目的

技術釣りリポジトリの変更を、古い作業や無関係な差分を混ぜずに、責務ごとのレビュー可能なPRとして届ける。マージや本番反映まで依頼された場合は、既存のCloud Run設定を維持し、反映後の稼働まで検証する。

日本語で作業状況と最終結果を伝える。ユーザーの「全部」は、見つかった差分・PRの全件を棚卸しして報告する意味として扱い、無関係な変更を強制的に統合したり、未承認の本番操作を行う許可とは解釈しない。

## 境界と安全性

- PR作成・push・マージ・Cloud Runデプロイは外部状態を変える。ユーザーがその操作を明示的に依頼した範囲だけ実施する。このスキルの存在だけで許可を推定しない。
- 作業開始時に現在のブランチ、追跡先、HEAD、staged/unstaged/untracked、stash、remote、既存PRを記録する。ユーザーの変更を消さない。
- `reset --hard`、強制push、stash削除、無確認のブランチ切替・上書きはしない。差分を退避する場合は復元可能性を確認し、stash IDと内容を記録する。退避した変更を勝手にdropしない。
- 既存のローカル `main` がremoteの既定ブランチと異なる場合、`main`を作り直したりポインタを動かしたりしない。remoteの既定ブランチを基準に作業し、既存ローカル状態を保全する。
- 秘密情報、トークン、パスワードをskill・ログ・PR本文へ書かない。ユーザーが会話に貼った認証情報も再掲しない。
- Cloud Runはデプロイ依頼がある場合だけ扱う。Origin、環境変数、CPU/メモリ、min/max instances、同時実行数、スケーリング、課金設定などは変更しない。設定変更が別途必要なら、デプロイと分離して許可を得る。

## 1. 差分とPRを全件棚卸しする

1. `git status --short --branch`、`git diff`、`git diff --cached`、untracked一覧、直近log、remote/追跡先を確認する。レビュー対象のファイルだけでなく、リポジトリ内の全差分を把握する。
2. remoteの既定ブランチとGitHubのopen PRを読み取り専用で取得する。必要なら最新情報をfetchするが、ローカルブランチを強制的に移動しない。
3. 各差分を最新のremote既定ブランチおよび既存PRと比較し、次を分類する。
   - すでにマージ済み、または新しい実装で置き換わった
   - 古い挙動へ戻す、ユーザーの明示的な選好と衝突する
   - 独立して出せる未完了変更
   - 他の変更に依存する、競合する、あるいは現状では意図が不明
4. 古い作業を「まだ差分がある」という理由だけで復活させない。除外したものも理由と保全場所を記録し、未完了項目として報告する。
5. 差分が大きい場合は変更一覧を先に作り、ファイル単位ではなくユーザー価値と変更理由でグループ化する。

## 2. 単一責任でPRに分ける

- 1つのPRは1つのユーザー価値または技術的責務に限定する。無関係な修正、書式変更、デプロイ設定変更を抱き合わせない。
- 変更を分ける際は、各PRが独立してビルド・テストできるか、順序依存があるかを先に確認する。必要な依存PRは本文で明記する。
- パフォーマンス改善で「見た目を変えない」とする場合、数値やスクリーンショットだけでなく、ブラウザーで同じ状態を比較する。視覚確認できない場合は、その未検証を明記し、見た目不変を断言しない。
- 変更前に既存テストの期待値を読み、実装の問題をテスト緩和で隠さない。
- 各PRの日本語タイトル・本文には、目的、主な変更、検証結果、未検証事項、依存関係を含める。コミットも責務に沿って分ける。

## 3. 検証とレビュー

1. リポジトリで定義されたテスト、型検査、lint/buildを実行する。失敗は既存失敗と今回の回帰を区別し、修正した場合は関連検証を再実行する。
2. PR差分をベースブランチから読み直し、境界条件、後方互換性、状態遷移、リソース解放、ユーザーが見える挙動、テスト不足をレビューする。
3. PR CIの完了を確認する。自分のPRはGitHub上でapproveできないため、自己承認を装わず、レビュー所見を記録し必要なら通常コメントとして投稿する。
4. P0/P1相当の未解決問題、失敗CI、未確認の競合があればマージを止め、証拠と次の対応を伝える。
5. ユーザーがマージまで明示した場合のみ、全ての必須チェックが緑であることを確認してマージする。マージ後にremote既定ブランチの新しいHEADとCIも確認する。
6. ローカル作業を同期する場合、cleanでfast-forward可能なときだけ安全に進める。分岐・dirty状態なら上書きせず、状態を保ったまま報告する。

## 4. Cloud Runを更新する場合

Cloud Run更新も明示的に依頼され、対象サービスが明確な場合だけ実施する。

1. デプロイ前に対象project/service/region、現在のready revision、traffic、URL、環境変数名、CPU、memory、scale、concurrency、ingressなど現行設定を読み取り専用で記録する。リポジトリ設定と実サービス設定の両方を確認し、対象を推測しない。
2. デプロイするコードがマージ済みの意図したcommitに由来することを確認する。ビルドとデプロイのコマンド・ログ・成果物を紐づける。
3. 可能ならビルド済み成果物のimmutable digestをデプロイする。`gcloud run deploy --source` が失敗を返した場合、すぐ再実行や別成果物の反映をしない。Cloud Buildを対象regionで調査し、ビルド成功、ソース内容、出力digestを確認する。意図したコードのdigestが確認できた場合に限ってそのdigestを使う。原因・結果が曖昧なら停止する。
4. デプロイコマンドには必要なimage/source・service・regionだけを指定し、現行設定を変えるフラグを付けない。デプロイ前後を比較し、意図しない設定変更があれば追加変更を止めて報告する。
5. revisionがReady、期待するtraffic割合、`status.url`を確認する。`/health`と`/ready`（またはサービスが定めるhealth endpoint）を実際にHTTP確認し、代表画面/主要フローも可能な範囲でsmoke testする。デプロイ出力に表示されたURLが常にcanonicalとは限らないため、service statusからURLを取得する。
6. 結果ではrevision、traffic、URL、health結果、設定差分の有無を報告する。Cloud Build/Artifact Registry/Cloud Runの利用料金が完全にゼロとは断言せず、料金が不明なら「追加費用なし」と約束しない。

## 完了報告

簡潔な日本語で、次を区別して報告する。

- PRごとの責務、URL、commit/merge結果
- 実行したテスト・型検査・build・CIと結果
- レビューで見つけた問題、未対応事項、除外して保全した差分
- デプロイした場合のrevision・traffic・URL・health・設定維持の確認
- 確認できなかったこと、残るリスク、費用について断言できない点

成功していない工程を完了扱いにしない。実ブラウザーや実機を確認していないのに確認済みと書かない。
